# System Architecture Overview: LabFlow Test Automation

---

## 1. Automation Framework & Language Stack

- **Language & Runtime:** Java 17 (LTS) — required by the project brief; LTS gives a stable, well-supported baseline for `record`-based domain models and modern language features.
- **Build Tool:** Maven, multi-module. **Five framework modules today** — `common` (the lab's shared concepts and configuration), `test-data` (since spec 005: the shared test-data recipes), `api-client` (the only code that talks to the lab's API), `api-tests` (the workflow checks) and, since spec 004, `ui-tests` (screen checks) — under a root parent `pom.xml` (groupId `com.labflow`). No empty placeholder modules: each one arrived when it had code.
  - **Module dependencies (spec 005):** `test-data` depends on `common` only and holds plain values (it never calls the lab), so it stays free of HTTP; `api-tests` and `ui-tests` use it at `test` scope, because only the checks build data. `common` has one runtime dependency, `slf4j-api` (the logging API, no implementation), and the JUnit APIs (`junit-jupiter-api`, `junit-platform-engine`, `junit-platform-launcher`) at `provided` scope, to compile the labels, `ChecksAtOnceStrategy` and `CheckCountListener` without passing JUnit on to consumers, which already bring it at test scope. (Spec 007 added `allure-junit-platform` at `provided` scope to compile `LabChecksAllureListener`; spec 008 deleted both, because only Allure's Cucumber adapter records now.) These JUnit helpers live in `common` rather than a sixth "test-support" module. `logback-classic` is test-scoped wherever it is used. A **root Maven Wrapper** (`./mvnw`, script-only, Maven 3.10.0 since 2026-10-12 — the same version as the lab's own wrapper) means only a JDK is needed. `maven.compiler.release=17` enforces Java 17 on any newer JDK (developed on JDK 26; since spec 006, CI pins Temurin JDK 17). Checks run under **Surefire** (settings at their defaults except for two deliberate changes, below), not Failsafe: they neither start nor stop the lab, so there is no teardown phase for Failsafe to protect and "one command" stays `test`. _Alternative: Failsafe_ — worth it if slow lab-dependent tests must later be separated from fast ones (or use tags in Phase 2).
  - **Readable names in reports (spec 004):** the root `pluginManagement` configures Surefire's JUnit 5 reporters (`JUnit5Xml30StatelessReporter`, `JUnit5StatelessTestsetInfoReporter`) with phrased names. Every module's `TEST-*.xml` then lists each self-check, including each parameterized row, under its `@DisplayName`, and (since spec 008) each scenario, including each outline row, under its short scenario name (Cucumber's `short` naming strategy, see "The check layer" below). Report file names and the XML `classname` stay the Java class name (for a scenario, its suite class `WorkflowScenariosTest` or `ScreenScenariosTest`), so tooling can still link results to source. Surefire's console never lists passing tests one by one.
  - **Formatting and coverage (tech-debt cleanup, 2026-10-11):** two plugins in the root `pom.xml`, inherited by every module, with the same pair copied into `mock-lab-app/pom.xml` because the lab is a separate build.
    - **Spotless** with deliberately light rules (no unused imports, no trailing spaces, spaces not tabs, final newline), so adopting it caused no mass reformat. It is not bound to a build phase: `./mvnw spotless:check` is an explicit step in CI's Build job and `./mvnw spotless:apply` fixes files. _Rejected:_ google-java-format, which would rewrite nearly every file to a 100-column style.
    - **JaCoCo** (`prepare-agent` plus `report` at the `test` phase) writes `target/site/jacoco/` per module on every test run. No minimum is enforced. JaCoCo sets Surefire's `argLine` property, so a future `argLine` in Surefire's configuration must include `@{argLine}`.
  - **Whole-run time limit for `ui-tests` (spec 004):** the `surefire.timeout=600` property (Surefire's `forkedProcessTimeoutInSeconds`) kills a forked test JVM that is stuck for 10 minutes. It is set as a property rather than in the plugin `<configuration>`, so `-Dsurefire.timeout=…` can still override it.
- **Test Execution Framework:** JUnit 5 (the 5.14 line via the JUnit BOM). The JUnit Platform runs two engines in one `./mvnw test`: Jupiter for the framework's own self-checks (parameterized tests, the built-in parallel engine) and, since spec 008, the Cucumber engine for the lab checks (next bullet). Tags (`api`, `ui`, `smoke`, `regression`) work across both. Both run in random order to prove independence (Jupiter: classes and methods; Cucumber: `cucumber.execution.order=random`); this stays on under parallel execution.
  - **The check layer (spec 008):** every lab check is a Gherkin scenario (Given / When / Then in plain language) in a feature file, run by **Cucumber-JVM 7.34.9** (`cucumber-bom`, `cucumber.version` in the root `pom.xml`) on the same JUnit Platform: 47 workflow checks and 16 screen checks, an outline row counted as one check. Step definitions call the same `api-client` services and Page Objects as the Jupiter checks did, so nothing below the checks changed. _Why:_ readable scenarios make the visual report understandable (the decision of 2026-10-12, see "Behaviour-driven layer" below).
    - **One `@Suite` runner per module:** `WorkflowScenariosTest` (`api-tests`) and `ScreenScenariosTest` (`ui-tests`), each `@IncludeEngines("cucumber")` and `@SelectPackages("features")`, with no code of their own. _Why a suite class:_ Surefire reports only tests that belong to a class. In the proving slice (2026-10-18) the engine finding the feature files by itself (`cucumber.features`) ran every scenario but Surefire reported `Tests run: 48`, so a failing scenario would not have failed the build. Through the suite class every scenario is a test of that class, and `-Dgroups`, the pre-flight listener and `CheckCountListener` work unchanged. The engine's settings (glue packages, parallel strategy, order, naming, the Allure plugin) are in each check module's `junit-platform.properties`.
    - **The 7.x line on purpose:** Cucumber 8.0 is built against JUnit 6 (its engine builds against Jupiter 6.1.3); 7.34.9 builds against Jupiter 5.14 and needs only `junit-platform-engine`, the same situation as Allure 2.x against 3.0. Dependabot's "ignore major versions" rule keeps it on 7.x; 7.34.9 may be the last 7.x release.
    - **New dependencies (spec 008), test scope in `api-tests` and `ui-tests`, versions from the BOMs:** `cucumber-java` (step definitions and hooks as annotated methods), `cucumber-junit-platform-engine` (the engine that runs the scenarios inside `./mvnw test`), `junit-platform-suite` (the `@Suite` runner above; version from the JUnit BOM), `cucumber-picocontainer` (constructor injection, so step and hook classes share one world object per scenario; Cucumber's default object factory cannot share state between classes) and `allure-cucumber7-jvm` (records the report, see "Visual report adapter").
    - **Hooks and a world instead of Jupiter extensions and base classes:** Jupiter extensions do not apply to scenarios. One world object per scenario, `LabWorld` / `UiWorld`, holds the client, the page (screens), the records the scenario created, the last answer and the data helpers that `LabTest` / `UiTest` used to hold. Hook classes, `ScenarioHooks` (`api-tests`) and `UiHooks` (`ui-tests`), do what the extensions did: put the check name into the run log (see Logging), set the report's grouping labels and, for screens, open and close the browser page, keep failure evidence and start the time limit. `LabTest`, `UiTest`, `BrowserExtension`, both `ScenarioNameExtension`s, `CheckNameInterceptor` and `LabChecksAllureListener` were deleted in spec 008.
    - **Module layout (spec 008, the same in both check modules):** feature files in `<module>/src/test/features/`, one per topic, named with the topic's number (`01-getting-access.feature`), declared as a test resource with `targetPath` `features`, so they are on the classpath as `features/` (`src/test/resources/` keeps only configuration). Under the module's test package: the runner at the root; `steps/` with one `<Topic>Steps` class per feature (`GettingAccessSteps` for `01-getting-access.feature`); `hooks/`; `world/`; `framework/` for the machinery, by concern (`browser/`, `evidence/`, `preflight/`, `watchdog/` in `ui-tests`; `log/`, `preflight/` in `api-tests`); and `selfcheck/` for the framework's own tests (`guards/` with their `support/` helpers, `framework/` for the tests of the machinery). Only `steps` and `hooks` are glue packages (`cucumber.glue`).
    - **Self-checks stay Jupiter tests** and are never recorded in the report. Among them, `DryRunGuardTest` runs the feature files in Cucumber's dry-run mode and fails on a Gherkin line no step matches (naming the line and its file) and on a step definition no line uses; `FeatureFilesGuardTest` pins the counts (47 and 16), names of at most 45 characters and unique per topic, the topic numbering (the same in both families) and no secret in a feature file. `RunLogSecrecyGuardTest` (the run log holds neither a patient name nor the access key) was a lab check until spec 008; by the owner's decision (2026-10-12) it is a self-check, still run against the lab but with no family label, so it is not counted or reported as a lab check.
  - **Labels (spec 005; Gherkin tags since spec 008):** JUnit tags `api`, `ui`, `smoke`, `regression`. Since spec 008 they are Gherkin tags: `@api` or `@ui` plus `@regression` on each `Feature:` line (a scenario carries its feature's tags), `@smoke` on 6 key scenarios (3 per family), and `@accepted` or `@refused` on each scenario for the report's sub-group. The Cucumber engine exposes Gherkin tags as JUnit Platform tags, so `-Dgroups` and `Labels.isLabCheck` work as before. `LabelGuardTest` pins one family tag per feature, one sub-group tag per scenario and the smoke list. (From spec 005 until spec 008 the tags were composed annotations in `common`, `@ApiCheck`, `@UiCheck`, `@Smoke`, `@Regression`, carried by the base classes `LabTest` and `UiTest`; the annotations still exist in `common`, but no check uses them.) Subsets use Surefire's standard `-Dgroups=<tag expression>` with no profiles; smoke is `smoke | !(api | ui)`, which also keeps the untagged self-checks. One `CheckCountListener` in `common`, registered by each test module through `META-INF/services`, logs `Lab checks run: N (labels: …)`, so a label that matches nothing visibly reports 0.
  - **Parallel execution (spec 005):** enabled in both `api-tests` and `ui-tests`; classes and methods run concurrently in one forked JVM (no Maven `-T`). A small custom `ChecksAtOnceStrategy` in `common` sets the pool size from `-DchecksAtOnce=N`, defaulting to the number of cores, with parallelism = core = max pool = N and a saturate predicate of `true`, so no more than N checks run at once. _Why custom:_ JUnit's `fixed` strategy cannot default to the core count and `dynamic` cannot take an exact N. JUnit prefixes the parameters it hands a custom strategy (`junit.jupiter.execution.parallel.config.`), so the strategy reads the short `checksAtOnce` system property itself. `RecordingPauseTest`, a self-test with its own static Playwright, is `@Isolated`. Since spec 008 the Cucumber engine takes the same strategy (`cucumber.execution.parallel.enabled=true`, `cucumber.execution.parallel.config.custom.class=com.labflow.common.junit.ChecksAtOnceStrategy`), so `-DchecksAtOnce=N` limits the scenarios too. In the proving slice the two engines ran one after the other (the Jupiter lab checks of that time finished before the first scenario started); whether the self-checks ever overlap the scenarios was not measured.
  - **Time limits in layers (spec 004, `ui-tests`; the per-check layer rebuilt in spec 008):**
    - Playwright caps every wait at 30 s.
    - Each screen scenario has 2 minutes. Cucumber has no per-scenario time limit and nothing like JUnit's `SEPARATE_THREAD` mode, so `ScenarioWatchdog` (`ui-tests`, `framework/watchdog/`) stands in: `UiHooks` starts it before the page is opened and cancels it after the page is closed; when 2 minutes pass first, it logs the scenario's name and a dump of every thread at ERROR and interrupts the scenario's thread. _Accepted behaviour change (owner, 2026-10-12):_ a call that ignores interruption can no longer be abandoned for one check while the others go on, as JUnit's `SEPARATE_THREAD` limit did until spec 008; it now stays stuck and the next layer fails the whole run. JUnit's 2-minute limit (`junit.jupiter.execution.timeout.default=2m`, `SEPARATE_THREAD`) still covers the Jupiter self-checks that open a browser.
    - Surefire's 10-minute fork limit (above) covers what the watchdog cannot free: a stuck call that ignores interruption, and the browser launch, `newContext`, tracing and `close` calls in the hooks. Playwright offers no timeout on those.
  - **Visual report adapter (spec 007; Cucumber adapter since spec 008):** an Allure adapter records one small result file per lab check while the checks run; the report itself is built separately and only on request (see Observability & Reporting). Until spec 008 that was Allure's JUnit 5 adapter; since then it is Allure's Cucumber adapter, `allure-cucumber7-jvm` (2.35.5, from the Allure BOM), registered as a Cucumber plugin with `cucumber.plugin=io.qameta.allure.cucumber7jvm.AllureCucumber7Jvm` in each check module's `junit-platform.properties`. It records each scenario with its Gherkin lines, word for word, as the result's steps, so a failed line shows as failed and the lines after it as skipped. It uses the same Allure lifecycle and results folder, so `report.sh` and the Report job did not change. The adapter declares no Cucumber version; its pairing with Cucumber 7.34.9 was confirmed at run time in the proving slice.
    - **The 2.x line on purpose:** `allure-bom` **2.35.5** is imported in the root `pom.xml`. Allure 3.0 is built against JUnit 6 and this project is on JUnit 5.14; Dependabot's "ignore major versions" rule keeps it on 2.x. The report plugin `allure-maven` 3.1.0 and the report tool Allure Report 2.46.1 are pinned in the same properties block.
    - **Where the adapter sits:** `allure-cucumber7-jvm` at test scope in `api-tests` and `ui-tests`. `allure-jupiter` (spec 007's JUnit 5 adapter; its current name, `allure-junit5` being a relocation stub that makes Maven warn) is still declared there at test scope, but its listener is switched off (next bullet), so it records nothing. Since spec 008 `common` has no Allure dependency at all. `api-client` and `test-data` have no reporting library. No Java agent (AspectJ) is used: steps and attachments go through Allure's plain API.
    - **Only the lab checks are recorded:** since spec 008 every lab check is a Cucumber scenario and only Allure's Cucumber adapter records; `LabChecksAllureListener` (spec 007's filter in `common`, which forwarded a test's events to Allure only when `Labels.isLabCheck` accepted the tags) was deleted. `CheckCountListener` still counts with `Labels.isLabCheck`. _Why:_ Allure's own listener (`AllureJunitPlatform`) records every test, including the framework's self-checks, and the adapter has no tag filter. It comes in with `allure-jupiter` and registers itself through `ServiceLoader`, so it is switched off with the JUnit Platform parameter `junit.platform.execution.listeners.deactivate` in each check module's `junit-platform.properties`; that also stops it recording each scenario a second time. The self-checks, being Jupiter tests, are therefore never recorded. _Rejected:_ deleting unwanted result files after the run (fragile), and building the report only from a tag-filtered run (CI runs `regression | !(api | ui)` on purpose).
    - **Families, topics and names (spec 008):** the adapter sets `feature` to the Feature name (the numbered topic, e.g. "04. Registering a sample") and a default `story`. A `@Before` hook (`ScenarioHooks.labelTheReportEntry`, `UiHooks.labelTheReportEntry`) replaces the rest from the scenario's tags: `epic` = the family ("API tests" for `@api`, "UI tests" for `@ui`; named "Workflow checks" / "Screen checks" until 2026-10-18, like the CI jobs), `story` = the sub-group ("Accepted" / "Refused"), and `parentSuite` / `suite` / `subSuite` = family / topic / sub-group, so the Suites view is named in plain language too. The hook addresses the result by `scenario.getId()`, because during a `Before` hook the adapter's current test case is the fixture, not the scenario. The scenario's title is the check's name, and the free text under it is shown in the check's description. _Order:_ Allure Report 2.46 sorts groups by name only, so topics carry a two-digit number and checks inside a sub-group appear alphabetically. (Until spec 008, `@Epic` on `LabTest` / `UiTest` set the family and the `@DisplayName` the name.)
    - **One shared results folder:** both check modules write to `target/allure-results` at the repository root (`allure.properties` says `../target/allure-results`, relative because Surefire runs with the module as its working directory), so one report covers both families with no aggregation step. One `maven-clean-plugin` execution on the root project only (`<inherited>false</inherited>`, phase `initialize`, default directories excluded) deletes that folder and the previous built report (`target/site/allure-maven-plugin`) at the start of every root Maven run. The root is first in the reactor for every documented command, including `-pl api-tests -am`, so a second run never mixes with the first and a single-family run leaves nothing from the other family. _Consequence:_ any lifecycle command started from the root (even `test-compile`) removes the results, so the report is built straight after the checks; the report goal `allure:report` is a direct goal with no lifecycle and does not.
- **API Testing Library:** RestAssured 5.5.7 (confirmed in spec 003; the 5.x line matches JUnit 5 — RestAssured 6.x was not evaluated). _Alternative: Retrofit + OkHttp._ RestAssured is chosen as the default because it is purpose-built for test automation (fluent given/when/then assertions, minimal boilerplate for a small endpoint surface), whereas Retrofit is optimized for building typed production API clients — better justified when the focus is "client-library" design.
- **Assertions & JSON Mapping:** AssertJ (fluent assertions, readable failure messages, and the base for the custom rejection assertions; the lab's own tests already use it) and Jackson (`databind` plus `jsr310` for `Instant`, one shared lenient mapper) — chosen over JUnit's built-in assertions and Hamcrest for failure-message quality.
- **Client Layering:** Test → Service → Api → RestAssured. Api classes make one call per lab endpoint and never assert; service classes expose business verbs in two forms — a "happy" method (returns a domain object, fails loudly on an unexpected status) and an `attempt…` twin (returns a response wrapper with status, headers and body, for scenarios where a refusal is the expected result). Custom AssertJ assertions (`isRejectedAs(kind, message)`) keep rejection checks readable. RestAssured types stay out of the checks (enforced by a guard test), and only per-request specs are used (no static RestAssured defaults), which keeps parallel execution safe.
- **UI Automation Library:** Playwright for Java. _Alternative: Selenium WebDriver._ Playwright was the intended UI tool from the project's start (the repository was first named after it), and it also ships auto-waiting and bundled browser binaries, reducing flakiness compared to hand-rolled Selenium waits — a plus for the "avoid flaky UI tests" quality criterion. Page Object Model applies equally well to either.
  - **Confirmed and built in spec 004:** Playwright for Java, headless by default; built on **1.63.0**, now **1.64.0** (Dependabot update, PR #14, 2026-10-25). The version is pinned once, as `playwright.version` in the root `pom.xml`. **Browsers (spec 005):** Chromium (default) and WebKit, chosen with `BROWSER`/`-Dbrowser`. Firefox is not supported: Playwright's Firefox build does not start on the development machine (macOS 27), even outside the framework.
  - **`ui-tests` layout:**
    - Page Objects live in `src/main`: one per screen (`LoginPage`, `SampleListPage`, `CreateSamplePage`, `SampleDetailsPage`, `ReportPage`). JUnit and AssertJ are test-scoped, so the compiler keeps verdicts out of Page Objects.
    - Checks are scenarios in `src/test/features` and read as user workflows; their step definitions live in `src/test` (`steps/`, see "The check layer" above). Until spec 008 they were Jupiter classes in `happy/` and `rejection/`.
    - Navigation methods return the Page Object of the screen the user lands on. Outcomes are split by name (`signIn` vs `signInExpectingError`).
    - Only Page Objects know locators and screen URLs; step definitions never use them. Plain-text guard tests enforce this, as well as no fixed sleeps and no assertions in Page Objects.
  - **Test data:** each check prepares its data through `api-client` (values from the shared `test-data` recipes): a unique patient (the lab has no patient screen), and samples already partway through the workflow. Exactly one journey goes through every screen.
  - **Waiting:** Page Objects own synchronisation: each navigation returns only once the destination screen is ready, and `advance()` waits with `page.waitForCondition`. Checks compare resolved values with AssertJ. `PlaywrightAssertions` is not used.
  - **Browser lifecycle (spec 005; `BrowserPool` since spec 008):** one `Playwright` + `Browser` per worker thread, created lazily in a `ThreadLocal` by `BrowserPool` and remembered in one list that `UiHooks` closes once, in Cucumber's global `@AfterAll` hook, after the last scenario (until spec 008, `BrowserExtension` registered them in a JUnit root-store resource). _Why:_ Playwright for Java is not thread-safe per `Playwright` instance; one per check would start a driver process each time and cancel the speed-up. So a run has at most `checksAtOnce` browsers. A fresh `BrowserContext` + `Page` per check (its own browser window), opened in a `@Before` hook of `UiHooks`, is unchanged.
- **Behaviour-driven layer (spec 008):** every lab check is a Gherkin scenario run by Cucumber-JVM 7 (see "The check layer" above). The project brief marks Cucumber as optional and ranks it last (section 30), so it was first left out (decided 2026-10-11). On 2026-10-12 the owner reversed that decision, for every lab check, because readable scenarios are what makes the visual report understandable; the owner gave the go after the proving slice on 2026-10-18.

_Confirmed (spec 008): Cucumber-JVM 7.34.9 (not 8, which needs JUnit 6) on the JUnit Platform through one `@Suite` runner per module; Gherkin tags as the labels; a picocontainer world and Cucumber hooks instead of Jupiter base classes and extensions; Allure's Cucumber adapter as the only recorder, with grouping labels set in a hook; `ScenarioWatchdog` at 2 minutes plus Surefire's fork limit as the screen time limit; the run-log secrecy check moved to the self-checks. `LabTest`, `UiTest`, `BrowserExtension`, `CheckNameInterceptor` and `LabChecksAllureListener` were removed, and "no BDD layer" (2026-10-11) was reversed._

_Confirmed (spec 007): Allure Report on the 2.x adapter line (JUnit 5.14), recording only the lab checks through the filtering `LabChecksAllureListener` (replaced by the Cucumber adapter in spec 008); one shared results folder and one self-contained report for both families, built only through `.github/scripts/report.sh` with the tool's analytics off; request steps taken from the run log's request line instead of Allure's RestAssured filter; a fourth CI job, Report, that keeps the report with the run and can never change its verdict._

_Confirmed (spec 006): one GitHub Actions workflow (Build → API tests ∥ UI tests, named Workflow checks / Screen checks until 2026-10-18; since spec 007 a fourth job, Report, runs after both check jobs), each check job starting its own lab with `.github/scripts/lab.sh`; the access key chosen and masked in a step (secret, else the lab's default); job summaries from an in-repo `junit_summary.py` instead of a marketplace reporter; results kept as artifacts with the 90-day default retention._

_Confirmed (spec 005): labels as composed JUnit tags on the base classes (Gherkin tags since spec 008) and `-Dgroups` for subsets; JUnit's own parallel engine with the custom `ChecksAtOnceStrategy`; one Playwright + Browser per worker thread; Chromium and WebKit (no Firefox); a `test-data` module of plain-value recipes; SLF4J + Logback for the run log._

_Confirmed (spec 004): Playwright for Java over Selenium, Chromium only (WebKit added in spec 005); Page Objects in `ui-tests/src/main`._

## 2. System Under Test (Mock Lab Application)

_Phase 0 of the roadmap: since no real laboratory system exists to test against, this project builds its own minimal target application, kept structurally separate from the test framework itself._

- **Mock Backend Framework:** Spring Boot (Java) — a small REST service exposing the simulated lab workflow as JSON under the `/api` prefix (`/api/patients`, `/api/orders`, `/api/samples`) and enforcing the status state machine (Accessioned → ... → Report Generated), including the validation and error responses the negative test scenarios need. Processing progress, test result, and report are sample-scoped (`/api/samples/{id}/progress`, `/result`, `/report`) rather than separate top-level resources. A sample is moved to a requested stage with `PUT /api/samples/{id}/status`, and only the next stage is accepted. _Alternative: WireMock stub mappings or a Node.js `json-server`_ — simpler to stand up but harder to encode real state-transition logic and validation rules, which this project needs for meaningful negative testing.
- **URL Layout (JSON vs. screens):** The `/api` prefix keeps the JSON API apart from the Thymeleaf screens, which keep their own routes (`/samples`, `/samples/{id}`, `/samples/{id}/report`, `/login`). Both surfaces call the same service layer over the same in-memory data, so the lab rules are enforced identically and a sample created through either surface is visible in the other. _Alternative: serve JSON and HTML from the same paths via content negotiation_ — rejected because authentication behavior (redirect vs. 401) and error format would then depend on request headers.
- **Access Control (two isolated mechanisms, separated by path):** The screens use a session-based sign-in guard. The JSON API uses a shared access key sent as `Authorization: Bearer <key>`, checked by a servlet filter registered for `/api/*` only, with the key read from the `API_TOKEN` environment variable (a documented default applies for local runs; startup fails if it resolves to blank). The filter runs before routing, so a missing or wrong key yields 401 even for unknown routes or records. Neither mechanism reads the other's credentials. _Alternative: Spring Security_ — rejected as disproportionate for a mock target and out of line with the "no production-grade auth" non-goal.
- **Readiness Endpoint:** A small custom, unauthenticated `GET /health` returns 200 only once the application has finished starting **including** its seed data, and 503 before that. CI and local scripts poll it before running tests. _Alternative: Spring Boot Actuator's readiness probe_ — standard, but adds a dependency and needs extra security exclusions for no benefit at this scale.
- **Strict JSON Input:** The lab's JSON API parses request bodies strictly: a repeated key, or any content after the closing brace, is rejected as `400 "Malformed request body."` (Jackson strict duplicate detection and fail-on-trailing-tokens) rather than accepted leniently or failing with a server error. Test authors can rely on malformed-body checks behaving the same on every route.
- **In-Memory Data Store:** Plain in-memory Java collections (`ConcurrentHashMap`-backed repository classes). No H2 and no external database — matches the project brief's explicit "no complicated databases" guidance. Relationships: a Patient has many Orders, an Order has many Samples (one sample per sample type per order), and each Sample has one Processing Job, one Test Result, and one Report once those stages are reached.
- **Front-End Framework:** A minimal server-rendered UI via Spring Boot + Thymeleaf, serving the Login, Sample List, Create Sample, Sample Details, and Report screens directly from the same mock backend. _Alternative: a small standalone React/plain-JS single-page app calling the backend's REST API._ Thymeleaf is the default to avoid standing up a second toolchain (Node/npm) purely to host a throwaway UI — consistent with "do not over-engineer."
- **Location in Repo:** Lives in its own `mock-lab-app/` module, separate from the Maven multi-module automation framework, since it is the system under test, not the thing being delivered as the "product."

_Confirmed (spec 001): Spring Boot + Thymeleaf for the mock app, balancing realism with the project brief's "keep it small" guidance._

_Note (spec 002): the API's URL layout, access-key scheme, readiness endpoint, and error mapping are detailed in `context/spec/002-mock-lab-rest-api/technical-considerations.md`; this document records only the architectural decisions. The project brief's own example `POST /samples` therefore becomes `POST /api/samples` (the test framework's `BASE_URL` stays a plain host, and the API client adds the `/api` prefix)._

## 3. Test Data & Configuration

- **Test Data Generation (spec 005):** each check creates its own records, never relying on another check or on global lab state (checks never assert global counts). The values come from one shared place, the `test-data` module, used by both test modules: `Patients`, `Orders` and `Samples` recipes return plain draft records with valid defaults and named variations (e.g. `withoutName()`, `withRawType(…)`), and `UniqueData.name(kind)` gives `TEST-<kind>-<uuid>`. The fixed `TEST-` prefix marks every name as framework-made, and the UUID keeps it unique under parallel execution. Recipes never call the lab: a check passes the draft's fields to the existing service methods. _Rejected:_ recipes that call `LabClient`, which would couple the data module to HTTP. `CheckIndependenceGuardTest` (in both test modules) forbids `UUID.randomUUID` and hand-written name literals in the step, hook and world classes (check files until spec 008), so data comes only from the recipes.
- **Test Data Storage:** None persisted between runs — all test data is ephemeral, created against the mock backend at test time and not required to survive beyond the run (traceability comes from correlation IDs in logs, not a database).
- **Configuration Management:** The lab address comes from the `-DbaseUrl` system property, else the `BASE_URL` environment variable, else the chosen environment's default address, `http://localhost:8080` (the framework adds the `/api` prefix). The access key comes **only from the `API_TOKEN` environment variable** — the same name the lab itself reads — defaulting to the lab's documented local key (`mock-lab-local-token`, not a secret). It is deliberately **never accepted as a system property**: a `-D` value is written into Surefire's XML reports and is visible in the process list. Everything is loaded through a small typed `LabConfig` in `common`; the key is wrapped in a type whose `toString()` is `***`, and RestAssured's logging blacklists the `Authorization` header. Since spec 004:
  - The screen checks sign in with `MOCK_LAB_USERNAME` / `MOCK_LAB_PASSWORD`, the same names the lab reads. The defaults are the lab's documented local values, `LabTech` / `I_Like_This_Lab`.
  - The password is **environment-only**, like the access key, and is wrapped in a masking `Password` type (`UiCredentials` in `ui-tests`).
  - `-Dheaded=true` shows the browser and `-DslowMo=<ms>` slows it down. Both are debugging aids, not secrets.
  - Since spec 005, `ENVIRONMENT` (`local` default, or `ci`) and `BROWSER` (`chromium` default, or `webkit`) follow the same precedence rule: the `-Denvironment`/`-Dbrowser` system property, then the environment variable, then the default; names match ignoring case. An environment supplies only its default lab address and its name in the run output, and an explicit address always wins. `LabEnvironment` and `LabConfig` live in `common`, `BrowserChoice` in `ui-tests`.
  - The pre-flight listeners validate these settings before any check, so an unknown value stops the run with one message naming the value and listing the known ones. They then log one INFO banner (`Lab run: environment=… address=… key=***`, plus `browser=…` in `ui-tests`) before probing the lab. The key is never read for the banner.
  - `-DchecksAtOnce=N` (see JUnit above) and `-DlogBodies=true` / `LOG_BODIES` (see Logging) are the other two run options. _Alternative: the Owner library_ for annotation-driven config binding — unnecessary at this project's scale.

## 4. Infrastructure & Deployment

- **CI/CD (spec 006; the Report job is spec 007):** GitHub Actions, one workflow `.github/workflows/ci.yml` with four jobs.
  - **Triggers:** every push (all branches), pull requests into `main`, and `workflow_dispatch` (hand-started, with inputs `family` = `both`|`api`|`ui` and `browser` = `chromium`|`webkit`).
  - `permissions: contents: read` (least privilege). No `concurrency` block on purpose: two quick pushes both finish, so every commit gets its own verdict (the user's decision).
  - **Jobs**, all on pinned `ubuntu-24.04` (not `ubuntu-latest`, so the image cannot change under us) with a 15-minute timeout: **Build** (the gitleaks secret scan over the whole history, the Spotless formatting check for the reactor and the lab, then `test-compile` of every module, then the lab-free self-checks of `common`, `test-data` and `api-client`) → **API tests** ∥ **UI tests** (named Workflow checks / Screen checks until 2026-10-18), each `needs: build`, so a broken build skips both. Each check job runs `./mvnw -B -ntp -pl <module> -am test -Dgroups="regression | !(api | ui)"`: the regression lab checks plus that module's own self-checks, which run here rather than in Build because the module's pre-flight listener needs a running lab before any tag filter applies. A fourth job, **Report**, runs after both check jobs (next bullet).
  - **Report job (spec 007):** `report`, `needs: [build, api-tests, ui-tests]`, builds the one Allure report of the run and keeps it as an artifact.
    - **When it runs:** `if: ${{ !cancelled() && needs.build.result == 'success' }}`. `!cancelled()` lifts the default "skip when a needed job failed or was skipped", so the report is built when a check job failed and when a hand-started run skipped one family; the Build condition means a broken build skips it (grey, not red).
    - **Out of the verdict:** `continue-on-error: true` at job level, and on no step. A step that really breaks turns this job red while the run's verdict still comes from Build and the check jobs. So `Report` must not be a required check for merging.
    - **Collecting the results:** both "Keep the results" artifacts now also carry `target/allure-results/`. The job downloads them with `actions/download-artifact@v8` by `pattern` (not by `name`, because after a re-run of one job the other family's newest artifact is still attempt 1), each family into its own folder under `$RUNNER_TEMP`. A shell step then takes, per family, the artifact with the **highest attempt number** and copies its result files into `target/allure-results`. _Why:_ artifacts belong to the run, not the attempt, so a re-run also sees attempt 1's files; the highest attempt per family gives the re-run job's fresh results plus the other family's latest, and no check twice. The step accepts both download layouts, because the action unpacks exactly one match straight into `path` and several matches into one sub-folder each.
    - **Building and keeping:** `.github/scripts/report.sh` (the only way the report is built, see Observability & Reporting), then `index.html` is uploaded as `allure-report-<browser>-<attempt>`, so a re-run's report does not replace the first attempt's. Both steps are skipped when no result file was collected.
    - **A missing report is explained:** a last step with `if: always()` writes a `::warning title=Allure report missing::<reason>` annotation and one line in the job summary, telling apart "no result files", a failed download, a failed script and a failed upload. With no result files the job stays green with that warning: nothing in reporting broke, and the check job that kept no results is red already.
    - _Why a fourth job and not a step:_ the two check jobs run on different machines, so only something that runs after both sees both sets of result files. _Rejected:_ both families in one job (loses spec 006's separately re-runnable jobs), two reports (the decision is one combined report), and no report in CI.
  - **Secret scan:** the Build job downloads one pinned gitleaks release, verifies its SHA-256, and runs `gitleaks git . --redact` over the full history (`fetch-depth: 0` on that checkout). Rules are the defaults plus one allowlist in `.gitleaks.toml` for the `s3cret-` prefix that marks made-up secrets in self-tests. _Why not the gitleaks action:_ it is a third-party action to pin and trust, and it needs a licence for organisation accounts. Dependabot does not update this pin.
  - **Agent guard:** `.claude/settings.json` registers a `PreToolUse` hook, `.claude/hooks/block_sensitive_files.py`, that blocks an AI agent's Read/Edit/Write of `.env` files and private keys, and a shell command that passes such a file to a file-reading program. It is best effort for shell commands and fails open on unreadable input.
  - **Dependency updates:** `.github/dependabot.yml` asks Dependabot for weekly grouped minor and patch updates for three targets: the reactor (`/`), the lab (`/mock-lab-app`) and the GitHub Actions. Major versions are ignored on purpose. Every such pull request runs this workflow.
  - **Build warms the Maven cache for the check jobs:** besides packaging the lab, Build runs the Playwright CLI once with a harmless argument (`./mvnw -N exec:java -Dexec.args="--version"`). _Why:_ the cache is saved by Build, and nothing else there used `exec-maven-plugin`, so the UI tests job (then Screen checks) fetched it from Maven Central live in "Install the browser"; a one-second outage there failed that job once (run 38224248594, 2026-10-12). The cache is written only when its key (every `pom.xml`) is new, so a new warm-up takes effect from the first Build after a pom change. The Report job still downloads the Allure tool live; it cannot change the run's verdict.
  - **Actions (majors):** `actions/checkout@v7`, `actions/setup-java@v6` (Temurin 17, `cache: maven`), `actions/cache@v6`, `actions/upload-artifact@v7` and, since spec 007, `actions/download-artifact@v8` (the major released together with `upload-artifact@v7`).
  - **Access key in CI:** each check job has a "Choose the access key" step that runs the shared `.github/scripts/access_key.sh`: the repository secret `API_TOKEN` if set, else the default parsed from `mock-lab-app`'s `application.yml` (`${API_TOKEN:<default>}`, the single source of truth, no key literal in the workflow). It is masked with `::add-mask::` before being exported through `$GITHUB_ENV`, so lab and framework get the same value. _Why not job-level `env`:_ the runner prints each step's env header before any `::add-mask::` runs, so the key leaked once in the log (found in Slice 2). _Why the fallback is mandatory:_ an unset secret expands to `""`; Spring's `${API_TOKEN:default}` falls back only when the variable is missing, so the lab would accept an empty key, while the framework treats blank as unset and sends the default → every check gets 401.
  - **Browsers in CI:** `actions/cache` on `~/.cache/ms-playwright` keyed `playwright-<os>-<Playwright version>-<browser>`; `install --with-deps <browser>` runs every time, because the apt libraries it installs live outside the cache and vanish with each runner VM (on a cache hit only the apt part costs time); `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` on the test step. WebKit is chosen through a hand-started run.
  - **Private repository:** GitHub-hosted runners have 2 vCPU (so `checksAtOnce` defaults to 2) and 2000 free Actions minutes a month (a run is a few runner-minutes); the README badge renders only for viewers with access.
- **Running the System Under Test:** The `mock-lab-app` ships its own Maven Wrapper (`mvnw`), so only a JDK is needed to build and run it. Locally: `cd mock-lab-app && ./mvnw spring-boot:run`. In CI (spec 006), each check job starts its own lab on its own runner VM with `.github/scripts/lab.sh start`: it builds the jar (`./mvnw -q package -DskipTests`; the jar name is fixed via the build's final name), starts it with `nohup java -jar … &`, and polls `GET /health` once a second for up to 60 s, failing early if the process dies. On timeout it writes a `::error` annotation and the tail of `lab-startup.log`. `lab.sh stop` runs with `if: always()`. `LAB_PORT` (default 8080) lets the script run locally beside an engineer's own lab. `/login` is not a valid readiness signal because the port opens before seed data is loaded. _Alternative: Docker Compose_, wrapping the mock app in a container for one-command startup — worth adopting only if local setup friction becomes a real problem, per "do not over-engineer."
- **Running the Checks:** Start the lab first (see above), then from the repo root: `./mvnw clean test` runs everything; `./mvnw -pl api-tests -am test` runs the checks that use the lab plus the framework's quick self-checks. `-am` (`--also-make`) is required because `test` does not install sibling modules, so plain `-pl api-tests` cannot resolve them on a clean machine; `install` and `-q` are deliberately not part of the documented flow. The checks never build, start or stop the lab. In CI (spec 006) each check job starts the lab, waits for `/health`, then runs its module the same way (see CI/CD above). UI tests only: `./mvnw -pl ui-tests -am test` (reactor `common`, `test-data`, `api-client`, `ui-tests`). Since spec 005, subsets are picked with `-Dgroups` (see JUnit above). `./mvnw clean test` includes them; add `-fae` to get both verdicts when the API checks fail. `ui-tests` registers its own copy of the pre-flight listener, reusing `LabPreflight`.
- **Fail-Fast Pre-Flight:** A JUnit Platform `LauncherSessionListener` in `api-tests` checks once, before any test, that the lab answers `/health` and accepts the access key; otherwise the whole run stops with one greppable message (`LAB PRE-FLIGHT FAILED: …`) naming the address tried and how to start the lab. _Alternative: a per-class JUnit extension_ — rejected because it reports an error for every test class instead of stopping once. _Since spec 005:_ the listeners first validate the settings and log one banner (`key=***`), and run only for the first launcher session in the JVM, because self-tests that start a nested JUnit engine open more sessions in the same JVM.
- **Browser Automation Infra:** Playwright's bundled browser binaries, installed once with `./mvnw -N exec:java`. That command is `exec-maven-plugin` in the root POM with `<inherited>false</inherited>`, running Playwright's own CLI (`install chromium`) as a plugin dependency, so it needs no reactor build and no Node toolchain. On Linux CI, `-Dexec.args="install --with-deps <browser>"`. WebKit is installed once the same way, with `-Dexec.args="install webkit"`. The same plugin opens a trace: `-Dexec.args="show-trace <zip>"`. _Why not auto-download:_ `Playwright.create()` would silently fetch every browser, about 1 GB, inside the first test. So CI (spec 006) caches the browser folder and sets `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` for the test step (see CI/CD above). No Selenium Grid or separate browser provisioning is needed. _(There is no official `mvn playwright:install` plugin for Java; an earlier version of this document named one by mistake.)_

## 5. Observability & Reporting

- **Logging:** SLF4J + Logback across both the test framework and the mock app, capturing request method, endpoint, correlation/test ID, response status, and business identifiers — explicitly never credentials, tokens, or patient-identifying data, per the project brief's regulated-environment guidance. The mock app logs this way already; the test framework does too since spec 005:
  - `RequestLogFilter` (a RestAssured `Filter` in `api-client`, added to every request spec) writes one INFO line per request on logger `lab.http`: method, path, status, duration in ms, and the patient/order/sample identifiers from the path and the answer's id fields. It never writes headers (so never the access key), the query string, or names.
  - With `-DlogBodies=true` (or `LOG_BODIES`), request and answer bodies are also written, at DEBUG so they reach only the file, after `LogMasker` replaces every `name` and `password` value with `***`; a non-JSON body is logged only as its length.
  - A `@Before` scenario hook in each check module puts `<Feature> › <scenario>` into the SLF4J MDC under `RunLog.CHECK_NAME_KEY` (in `common`), and an `@After` hook removes it, so every line can be found by searching for the check. Cucumber runs a scenario's hooks and steps on one thread and MDC is thread-local, so it stays correct under parallel execution. (Until spec 008 this was `CheckNameInterceptor`, a JUnit `InvocationInterceptor`.)
  - Logback in each test module: console at INFO, and `target/logs/api-tests.log` / `target/logs/ui-tests.log` at DEBUG for `lab.http`, rewritten each run and removed by `clean`. The pattern includes the thread name.
  - `NoConsolePrintingGuardTest` keeps `System.out`/`System.err`/`printStackTrace` out of the framework, and the lab-backed `RunLogSecrecyGuardTest` proves the log file holds the sample identifier but neither the patient name nor the access key. It was the lab check `RunLogSecrecyTest` until spec 008; it is now a self-check (see "The check layer").
- **Test Reporting:** Maven Surefire reports and JUnit XML as the baseline (always available, no extra setup). Surefire's XML lists the JVM system properties, so secrets must never be passed as `-D` (see Configuration Management). Since spec 007 a visual report is added beside them, not instead of them (next bullet).
- **Visual report (spec 007):** Allure Report, one self-contained `target/site/allure-maven-plugin/index.html` covering both check families, which opens from disk with no server and no network. It is built only on request; a run without it behaves as before. How the result files are recorded is in section 1 ("Visual report adapter").
  - **Built only through `.github/scripts/report.sh`**, locally and in the Report job. The script runs `./mvnw -N allure:report` (`allure-maven`, declared on the root only, `singleFile`, the tool downloaded into the gitignored `.allure/`). _Why a script and not the bare goal:_ Allure Report 2.46.1 puts a Google Analytics tag into the page and sends an event to Google on every build, and both are switched off only by the environment variable `ALLURE_NO_ANALYTICS` set to exactly `true` (`1` leaves the tag in). `allure-maven` has no setting for it and the tool inherits the shell's environment, so the `pom.xml` cannot set it; the script exports it. The script also refuses to build when there is no `*-result.json` file (it removes a stale `index.html` and exits 1, because the tool would write an empty report), and fails if the built page still holds `googletagmanager`. _Not verified:_ that no request leaves the machine; this rests on the tool's own "analytics is disabled" log line, with no network capture.
  - **Request steps come from the run log, not from Allure's RestAssured filter.** `AllureStepAppender` (a Logback appender in `api-tests`, attached to the `lab.http` logger only) turns each INFO request line of `RequestLogFilter` into a step of the running check: method, path, status, duration and identifiers. The bodies of `-DlogBodies=true` are logged at DEBUG and are never forwarded, and a line logged while no check is running (the pre-flight) is skipped. Since spec 008 a request line nests under the Gherkin step that made it: Cucumber runs a scenario's hooks and steps on one thread and the adapter opens each step on that thread's Allure context, so steps land on the right check under parallel execution. UI tests get no request steps: the appender is attached only in `api-tests` (until spec 008 the reason was that a screen check's body ran on the `SEPARATE_THREAD` timeout thread). _Rejected:_ `allure-rest-assured`, whose filter attaches the raw request and answer, including the `Authorization` header and patient names. Reusing the log line keeps one place that decides what may be written down and keeps `api-client` free of any reporting library; the price is that a change to that line changes the report.
  - **Evidence for a failed screen check:** after `UiHooks` has saved `screenshot.png` and `trace.zip` (`BrowserExtension` until spec 008), `AllureEvidence` (reached through `ScenarioEvidence`) attaches whichever of the two exists. It does nothing when Allure has no running test case on the thread and logs and continues when a file cannot be attached, so the report can never turn a check red. A passing check attaches nothing. The single file grows when many screen checks fail, which is accepted at this suite's size; the trace is also still in the `screen-failures` artifact.
  - **What the report never contains:** the access key, the sign-in password (the trace is already free of it, see below), request or answer content, and headers. Patient names appear only as made-up `TEST-` names, inside a failure message or a failed screen check's picture and trace, as in the existing failure evidence.
  - **Guards:** `LabRunWiringTest` (`api-tests`) and `UiRunWiringGuardTest` (`ui-tests`) pin the deactivate line and the results folder; `NoAllureRequestCaptureGuardTest` forbids `allure-rest-assured` in every module's `pom.xml`; `CiWorkflowGuardTest` pins `ALLURE_NO_ANALYTICS=true` in the script, that the README and the workflow build the report only through the script, the four jobs, and the Report job's `needs`, `if`, `continue-on-error` and artifact name. `AllureStepAppenderTest` covers the appender's own rules.
- **Screen-check failure artifacts (spec 004):**
  - A failing screen check keeps a screenshot and a Playwright trace under `ui-tests/target/ui-failures/<browser>/<topic>/<scenario>-<line>/` (the browser level since spec 005, so a run in another browser never overwrites this one's evidence; topic and scenario instead of class and display name since spec 008).
  - Folder names are built only from the browser name, the sanitised topic and scenario names and the scenario's line number (which keeps the rows of an outline apart), never from values typed on a screen, so checks running side by side cannot collide.
  - Passing checks keep nothing.
  - The real password is kept out of traces. Experiments showed three leak paths: the `fill()` action log, DOM snapshots (Playwright records `type=password` values), and the network log of the sign-in POST. So sign-in (fill, submit, wait for the Sample List) runs with tracing stopped, and tracing restarts afterwards with the same options. `SignInTraceTest` proves that no trace entry holds the password. The trade-off is that a signed-in check's trace starts at the Sample List.
- **CI Test Summaries (spec 006):** `.github/scripts/junit_summary.py` (standard-library Python, always exits 0) turns each module's Surefire XML into Markdown: total/passed/failed/skipped/duration and each failing check by name with its expected-versus-actual. A `Summarise results` step (`if: always()`) pipes it through `tee -a "$GITHUB_STEP_SUMMARY"`, so it shows on the run page and in the job log. _Why not a marketplace reporter_ (e.g. `dorny/test-reporter`): check-run reporters need `checks: write`, which pull requests from forks do not get, and they add a third-party dependency to pin and trust.
- **CI Artifacts (spec 006):** uploaded with `if: always()`: `workflow-checks-results-<attempt>` and `screen-checks-results-<browser>-<attempt>` (Surefire reports, the run log, `lab-startup.log` and, since spec 007, the Allure result files in `target/allure-results/`); with `if: failure()`: `screen-failures-<browser>-<attempt>` (screenshots and traces). Since spec 007 the Report job adds `allure-report-<browser>-<attempt>` (the one `index.html`). The run attempt in the name keeps a re-run from clashing with the first attempt. Retention is GitHub's 90-day default. GitHub does not mask artifact contents; secrets stay out because the framework never writes them (`RunLogSecrecyGuardTest`, `SignInTraceTest`; grep-verified in Slice 5). Synthetic `TEST-` patient names may appear in screen evidence by design; in production, restrict access to such artifacts or mask that data.
