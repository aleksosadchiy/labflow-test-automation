# System Architecture Overview: Lab Workflow SDET Automation Framework

---

## 1. Automation Framework & Language Stack

- **Language & Runtime:** Java 17 (LTS) — required by the assignment; LTS gives a stable, well-supported baseline for `record`-based domain models and modern language features.
- **Build Tool:** Maven, multi-module. **Five framework modules today** — `common` (the lab's shared concepts and configuration), `test-data` (since spec 005: the shared test-data recipes), `api-client` (the only code that talks to the lab's API), `api-tests` (the workflow checks) and, since spec 004, `ui-tests` (screen checks) — under a root parent `pom.xml` (groupId `com.labflow`). No empty placeholder modules: each one arrived when it had code.
  - **Module dependencies (spec 005):** `test-data` depends on `common` only and holds plain values (it never calls the lab), so it stays free of HTTP; `api-tests` and `ui-tests` use it at `test` scope, because only the checks build data. `common` has one runtime dependency, `slf4j-api` (the logging API, no implementation), and the JUnit APIs (`junit-jupiter-api`, `junit-platform-engine`, `junit-platform-launcher`) at `provided` scope, to compile the labels, `ChecksAtOnceStrategy`, `CheckNameInterceptor` and `CheckCountListener` without passing JUnit on to consumers, which already bring it at test scope. These JUnit helpers live in `common` rather than a sixth "test-support" module. `logback-classic` is test-scoped wherever it is used. A **root Maven Wrapper** (`./mvnw`, script-only, Maven 3.9.11 — the same version as the lab's own wrapper) means only a JDK is needed. `maven.compiler.release=17` enforces Java 17 on any newer JDK (developed on JDK 26; since spec 006, CI pins Temurin JDK 17). Checks run under **Surefire** (settings at their defaults except for two deliberate changes, below), not Failsafe: they neither start nor stop the lab, so there is no teardown phase for Failsafe to protect and "one command" stays `test`. _Alternative: Failsafe_ — worth it if slow lab-dependent tests must later be separated from fast ones (or use tags in Phase 2).
  - **Readable names in reports (spec 004):** the root `pluginManagement` configures Surefire's JUnit 5 reporters (`JUnit5Xml30StatelessReporter`, `JUnit5StatelessTestsetInfoReporter`) with phrased names. Every module's `TEST-*.xml` then lists each check, including each parameterized row, under its `@DisplayName`. Report file names and the XML `classname` stay the Java class name, so tooling can still link results to source. Surefire's console never lists passing tests one by one.
  - **Formatting and coverage (tech-debt cleanup, 2026-10-11):** two plugins in the root `pom.xml`, inherited by every module, with the same pair copied into `mock-lab-app/pom.xml` because the lab is a separate build.
    - **Spotless** with deliberately light rules (no unused imports, no trailing spaces, spaces not tabs, final newline), so adopting it caused no mass reformat. It is not bound to a build phase: `./mvnw spotless:check` is an explicit step in CI's Build job and `./mvnw spotless:apply` fixes files. _Rejected:_ google-java-format, which would rewrite nearly every file to a 100-column style.
    - **JaCoCo** (`prepare-agent` plus `report` at the `test` phase) writes `target/site/jacoco/` per module on every test run. No minimum is enforced. JaCoCo sets Surefire's `argLine` property, so a future `argLine` in Surefire's configuration must include `@{argLine}`.
  - **Whole-run time limit for `ui-tests` (spec 004):** the `surefire.timeout=600` property (Surefire's `forkedProcessTimeoutInSeconds`) kills a forked test JVM that is stuck for 10 minutes. It is set as a property rather than in the plugin `<configuration>`, so `-Dsurefire.timeout=…` can still override it.
- **Test Execution Framework:** JUnit 5 (Jupiter, the 5.14 line via the JUnit BOM) — parameterized tests, tags (`api`, `ui`, `smoke`, `regression`), and the built-in parallel execution engine. Checks run in random order (classes and methods) to prove independence; this stays on under parallel execution.
  - **Labels (spec 005):** JUnit tags behind composed annotations in `common` (`@ApiCheck`, `@UiCheck`, `@Smoke`, `@Regression`), so a typo is a compile error, not a silently empty run. The base classes carry them: `LabTest` is `@ApiCheck @Regression`, `UiTest` is `@UiCheck @Regression`, so every check is labelled by construction. `@Smoke` sits on 6 key check methods (3 api, 3 ui), pinned by `LabelGuardTest`. Subsets use Surefire's standard `-Dgroups=<tag expression>` with no profiles; smoke is `smoke | !(api | ui)`, which also keeps the untagged self-checks. One `CheckCountListener` in `common`, registered by each test module through `META-INF/services`, logs `Lab checks run: N (labels: …)`, so a label that matches nothing visibly reports 0.
  - **Parallel execution (spec 005):** enabled in both `api-tests` and `ui-tests`; classes and methods run concurrently in one forked JVM (no Maven `-T`). A small custom `ChecksAtOnceStrategy` in `common` sets the pool size from `-DchecksAtOnce=N`, defaulting to the number of cores, with parallelism = core = max pool = N and a saturate predicate of `true`, so no more than N checks run at once. _Why custom:_ JUnit's `fixed` strategy cannot default to the core count and `dynamic` cannot take an exact N. JUnit prefixes the parameters it hands a custom strategy (`junit.jupiter.execution.parallel.config.`), so the strategy reads the short `checksAtOnce` system property itself. `RecordingPauseTest`, a self-test with its own static Playwright, is `@Isolated`.
  - **Time limits in layers (spec 004, `ui-tests`):**
    - Playwright caps every wait at 30 s.
    - JUnit caps each screen check at 2 minutes (`junit.jupiter.execution.timeout.default=2m`). A stuck check then fails under its `[Scenario: …]` name. The limit runs in `SEPARATE_THREAD` mode, because `SAME_THREAD` hung forever, in an experiment, on a wait that ignores interruption. The price is that the abandoned thread can disturb later checks; since spec 005 that is limited to the checks run by its own worker thread, which owns its own Playwright.
    - Surefire's 10-minute fork limit (above) covers what JUnit cannot reach: the browser launch, `newContext`, tracing and `close` calls in extension callbacks. Playwright offers no timeout on those.
- **API Testing Library:** RestAssured 5.5.7 (confirmed in spec 003; the 5.x line matches JUnit 5 — RestAssured 6.x was not evaluated). _Alternative: Retrofit + OkHttp._ RestAssured is chosen as the default because it is purpose-built for test automation (fluent given/when/then assertions, minimal boilerplate for a small endpoint surface), whereas Retrofit is optimized for building typed production API clients — better justified if the design discussion leans toward "client-library" design.
- **Assertions & JSON Mapping:** AssertJ (fluent assertions, readable failure messages, and the base for the custom rejection assertions; the lab's own tests already use it) and Jackson (`databind` plus `jsr310` for `Instant`, one shared lenient mapper) — chosen over JUnit's built-in assertions and Hamcrest for failure-message quality.
- **Client Layering:** Test → Service → Api → RestAssured. Api classes make one call per lab endpoint and never assert; service classes expose business verbs in two forms — a "happy" method (returns a domain object, fails loudly on an unexpected status) and an `attempt…` twin (returns a response wrapper with status, headers and body, for scenarios where a refusal is the expected result). Custom AssertJ assertions (`isRejectedAs(kind, message)`) keep rejection checks readable. RestAssured types stay out of the checks (enforced by a guard test), and only per-request specs are used (no static RestAssured defaults), which keeps parallel execution safe.
- **UI Automation Library:** Playwright for Java. _Alternative: Selenium WebDriver._ Playwright is the default given this repository's own name (`labflow-test-automation`), and it also ships auto-waiting and bundled browser binaries, reducing flakiness compared to hand-rolled Selenium waits — a plus for the "avoid flaky UI tests" evaluation criterion. Page Object Model applies equally well to either.
  - **Confirmed and built in spec 004:** Playwright for Java **1.63.0**, headless by default. **Browsers (spec 005):** Chromium (default) and WebKit, chosen with `BROWSER`/`-Dbrowser`. Firefox is not supported: Playwright's Firefox build does not start on the development machine (macOS 27), even outside the framework.
  - **`ui-tests` layout:**
    - Page Objects live in `src/main`: one per screen (`LoginPage`, `SampleListPage`, `CreateSamplePage`, `SampleDetailsPage`, `ReportPage`). JUnit and AssertJ are test-scoped, so the compiler keeps verdicts out of Page Objects.
    - Checks live in `src/test` (`happy/`, `rejection/`) and read as user workflows.
    - Navigation methods return the Page Object of the screen the user lands on. Outcomes are split by name (`signIn` vs `signInExpectingError`).
    - Only Page Objects know locators and screen URLs. Plain-text guard tests enforce this, as well as no fixed sleeps and no assertions in Page Objects.
  - **Test data:** each check prepares its data through `api-client` (values from the shared `test-data` recipes): a unique patient (the lab has no patient screen), and samples already partway through the workflow. Exactly one journey goes through every screen.
  - **Waiting:** Page Objects own synchronisation: each navigation returns only once the destination screen is ready, and `advance()` waits with `page.waitForCondition`. Checks compare resolved values with AssertJ. `PlaywrightAssertions` is not used.
  - **Browser lifecycle (spec 005):** one `Playwright` + `Browser` per JUnit worker thread, created lazily in a `ThreadLocal` and registered in one root-store resource that closes them all after the last check. _Why:_ Playwright for Java is not thread-safe per `Playwright` instance; one per check would start a driver process each time and cancel the speed-up. So a run has at most `checksAtOnce` browsers. A fresh `BrowserContext` + `Page` per check (its own browser window) is unchanged.
- **No BDD layer:** the assignment marks Cucumber as optional and ranks it last (section 30). It was deliberately left out (decided 2026-10-11), so there is no Cucumber-JVM or Gherkin in the project.

_Confirmed (spec 006): one GitHub Actions workflow (Build → Workflow checks ∥ Screen checks), each check job starting its own lab with `.github/scripts/lab.sh`; the access key chosen and masked in a step (secret, else the lab's default); job summaries from an in-repo `junit_summary.py` instead of a marketplace reporter; results kept as artifacts with the 90-day default retention._

_Confirmed (spec 005): labels as composed JUnit tags on the base classes and `-Dgroups` for subsets; JUnit's own parallel engine with the custom `ChecksAtOnceStrategy`; one Playwright + Browser per worker thread; Chromium and WebKit (no Firefox); a `test-data` module of plain-value recipes; SLF4J + Logback for the run log._

_Confirmed (spec 004): Playwright for Java over Selenium, Chromium only (WebKit added in spec 005); Page Objects in `ui-tests/src/main`._

_Confirmed (spec 003): RestAssured over Retrofit + OkHttp. Java 17 is the baseline, enforced with `maven.compiler.release=17` so any newer JDK produces compatible bytecode._

## 2. System Under Test (Mock Lab Application)

_Phase 0 of the roadmap: since no real laboratory system exists to test against, this project builds its own minimal target application, kept structurally separate from the test framework itself._

- **Mock Backend Framework:** Spring Boot (Java) — a small REST service exposing the simulated lab workflow as JSON under the `/api` prefix (`/api/patients`, `/api/orders`, `/api/samples`) and enforcing the status state machine (Accessioned → ... → Report Generated), including the validation and error responses the negative test scenarios need. Processing progress, test result, and report are sample-scoped (`/api/samples/{id}/progress`, `/result`, `/report`) rather than separate top-level resources. A sample is moved to a requested stage with `PUT /api/samples/{id}/status`, and only the next stage is accepted. _Alternative: WireMock stub mappings or a Node.js `json-server`_ — simpler to stand up but harder to encode real state-transition logic and validation rules, which this project needs for meaningful negative testing.
- **URL Layout (JSON vs. screens):** The `/api` prefix keeps the JSON API apart from the Thymeleaf screens, which keep their own routes (`/samples`, `/samples/{id}`, `/samples/{id}/report`, `/login`). Both surfaces call the same service layer over the same in-memory data, so the lab rules are enforced identically and a sample created through either surface is visible in the other. _Alternative: serve JSON and HTML from the same paths via content negotiation_ — rejected because authentication behavior (redirect vs. 401) and error format would then depend on request headers.
- **Access Control (two isolated mechanisms, separated by path):** The screens use a session-based sign-in guard. The JSON API uses a shared access key sent as `Authorization: Bearer <key>`, checked by a servlet filter registered for `/api/*` only, with the key read from the `API_TOKEN` environment variable (a documented default applies for local runs; startup fails if it resolves to blank). The filter runs before routing, so a missing or wrong key yields 401 even for unknown routes or records. Neither mechanism reads the other's credentials. _Alternative: Spring Security_ — rejected as disproportionate for a mock target and out of line with the "no production-grade auth" non-goal.
- **Readiness Endpoint:** A small custom, unauthenticated `GET /health` returns 200 only once the application has finished starting **including** its seed data, and 503 before that. CI and local scripts poll it before running tests. _Alternative: Spring Boot Actuator's readiness probe_ — standard, but adds a dependency and needs extra security exclusions for no benefit at this scale.
- **Strict JSON Input:** The lab's JSON API parses request bodies strictly: a repeated key, or any content after the closing brace, is rejected as `400 "Malformed request body."` (Jackson strict duplicate detection and fail-on-trailing-tokens) rather than accepted leniently or failing with a server error. Test authors can rely on malformed-body checks behaving the same on every route.
- **In-Memory Data Store:** Plain in-memory Java collections (`ConcurrentHashMap`-backed repository classes). No H2 and no external database — matches the assignment's explicit "no complicated databases" guidance. Relationships: a Patient has many Orders, an Order has many Samples (one sample per sample type per order), and each Sample has one Processing Job, one Test Result, and one Report once those stages are reached.
- **Front-End Framework:** A minimal server-rendered UI via Spring Boot + Thymeleaf, serving the Login, Sample List, Create Sample, Sample Details, and Report screens directly from the same mock backend. _Alternative: a small standalone React/plain-JS single-page app calling the backend's REST API._ Thymeleaf is the default to avoid standing up a second toolchain (Node/npm) purely to host a throwaway UI — consistent with "do not over-engineer."
- **Location in Repo:** Lives in its own `mock-lab-app/` module, separate from the Maven multi-module automation framework, since it is the system under test, not the thing being delivered as the "product."

_Confirmed (spec 001): Spring Boot + Thymeleaf for the mock app, balancing realism with the assignment's "keep it small" guidance._

_Note (spec 002): the API's URL layout, access-key scheme, readiness endpoint, and error mapping are detailed in `context/spec/002-mock-lab-rest-api/technical-considerations.md`; this document records only the architectural decisions. The assignment's own example `POST /samples` therefore becomes `POST /api/samples` (the test framework's `BASE_URL` stays a plain host, and the API client adds the `/api` prefix)._

## 3. Test Data & Configuration

- **Test Data Generation (spec 005):** each check creates its own records, never relying on another check or on global lab state (checks never assert global counts). The values come from one shared place, the `test-data` module, used by both test modules: `Patients`, `Orders` and `Samples` recipes return plain draft records with valid defaults and named variations (e.g. `withoutName()`, `withRawType(…)`), and `UniqueData.name(kind)` gives `TEST-<kind>-<uuid>`. The fixed `TEST-` prefix marks every name as framework-made, and the UUID keeps it unique under parallel execution. Recipes never call the lab: a check passes the draft's fields to the existing service methods. _Rejected:_ recipes that call `LabClient`, which would couple the data module to HTTP. `CheckIndependenceGuardTest` (in both test modules) forbids `UUID.randomUUID` and hand-written name literals in check files, so data comes only from the recipes.
- **Test Data Storage:** None persisted between runs — all test data is ephemeral, created against the mock backend at test time and not required to survive beyond the run (traceability comes from correlation IDs in logs, not a database).
- **Configuration Management:** The lab address comes from the `-DbaseUrl` system property, else the `BASE_URL` environment variable, else the chosen environment's default address, `http://localhost:8080` (the framework adds the `/api` prefix). The access key comes **only from the `API_TOKEN` environment variable** — the same name the lab itself reads — defaulting to the lab's documented local key (`mock-lab-local-token`, not a secret). It is deliberately **never accepted as a system property**: a `-D` value is written into Surefire's XML reports and is visible in the process list. Everything is loaded through a small typed `LabConfig` in `common`; the key is wrapped in a type whose `toString()` is `***`, and RestAssured's logging blacklists the `Authorization` header. Since spec 004:
  - The screen checks sign in with `MOCK_LAB_USERNAME` / `MOCK_LAB_PASSWORD`, the same names the lab reads. The defaults are the lab's documented local values, `LabTech` / `I_Like_This_Lab`.
  - The password is **environment-only**, like the access key, and is wrapped in a masking `Password` type (`UiCredentials` in `ui-tests`).
  - `-Dheaded=true` shows the browser and `-DslowMo=<ms>` slows it down. Both are debugging aids, not secrets.
  - Since spec 005, `ENVIRONMENT` (`local` default, or `ci`) and `BROWSER` (`chromium` default, or `webkit`) follow the same precedence rule: the `-Denvironment`/`-Dbrowser` system property, then the environment variable, then the default; names match ignoring case. An environment supplies only its default lab address and its name in the run output, and an explicit address always wins. `LabEnvironment` and `LabConfig` live in `common`, `BrowserChoice` in `ui-tests`.
  - The pre-flight listeners validate these settings before any check, so an unknown value stops the run with one message naming the value and listing the known ones. They then log one INFO banner (`Lab run: environment=… address=… key=***`, plus `browser=…` in `ui-tests`) before probing the lab. The key is never read for the banner.
  - `-DchecksAtOnce=N` (see JUnit above) and `-DlogBodies=true` / `LOG_BODIES` (see Logging) are the other two run options. _Alternative: the Owner library_ for annotation-driven config binding — unnecessary at this project's scale.

## 4. Infrastructure & Deployment

- **CI/CD (spec 006):** GitHub Actions, one workflow `.github/workflows/ci.yml`.
  - **Triggers:** every push (all branches), pull requests into `main`, and `workflow_dispatch` (hand-started, with inputs `family` = `both`|`api`|`ui` and `browser` = `chromium`|`webkit`).
  - `permissions: contents: read` (least privilege). No `concurrency` block on purpose: two quick pushes both finish, so every commit gets its own verdict (the user's decision).
  - **Jobs**, all on pinned `ubuntu-24.04` (not `ubuntu-latest`, so the image cannot change under us) with a 15-minute timeout: **Build** (the gitleaks secret scan over the whole history, the Spotless formatting check for the reactor and the lab, then `test-compile` of every module, then the lab-free self-checks of `common`, `test-data` and `api-client`) → **Workflow checks** ∥ **Screen checks**, each `needs: build`, so a broken build skips both. Each check job runs `./mvnw -B -ntp -pl <module> -am test -Dgroups="regression | !(api | ui)"`: the regression lab checks plus that module's own self-checks, which run here rather than in Build because the module's pre-flight listener needs a running lab before any tag filter applies.
  - **Secret scan:** the Build job downloads one pinned gitleaks release, verifies its SHA-256, and runs `gitleaks git . --redact` over the full history (`fetch-depth: 0` on that checkout). Rules are the defaults plus one allowlist in `.gitleaks.toml` for the `s3cret-` prefix that marks made-up secrets in self-tests. _Why not the gitleaks action:_ it is a third-party action to pin and trust, and it needs a licence for organisation accounts. Dependabot does not update this pin.
  - **Agent guard:** `.claude/settings.json` registers a `PreToolUse` hook, `.claude/hooks/block_sensitive_files.py`, that blocks an AI agent's Read/Edit/Write of `.env` files and private keys, and a shell command that passes such a file to a file-reading program. It is best effort for shell commands and fails open on unreadable input.
  - **Dependency updates:** `.github/dependabot.yml` asks Dependabot for weekly grouped minor and patch updates for three targets: the reactor (`/`), the lab (`/mock-lab-app`) and the GitHub Actions. Major versions are ignored on purpose. Every such pull request runs this workflow.
  - **Actions (majors):** `actions/checkout@v7`, `actions/setup-java@v6` (Temurin 17, `cache: maven`), `actions/cache@v6`, `actions/upload-artifact@v7`.
  - **Access key in CI:** each check job has a "Choose the access key" step that runs the shared `.github/scripts/access_key.sh`: the repository secret `API_TOKEN` if set, else the default parsed from `mock-lab-app`'s `application.yml` (`${API_TOKEN:<default>}`, the single source of truth, no key literal in the workflow). It is masked with `::add-mask::` before being exported through `$GITHUB_ENV`, so lab and framework get the same value. _Why not job-level `env`:_ the runner prints each step's env header before any `::add-mask::` runs, so the key leaked once in the log (found in Slice 2). _Why the fallback is mandatory:_ an unset secret expands to `""`; Spring's `${API_TOKEN:default}` falls back only when the variable is missing, so the lab would accept an empty key, while the framework treats blank as unset and sends the default → every check gets 401.
  - **Browsers in CI:** `actions/cache` on `~/.cache/ms-playwright` keyed `playwright-<os>-<Playwright version>-<browser>`; `install --with-deps <browser>` runs every time, because the apt libraries it installs live outside the cache and vanish with each runner VM (on a cache hit only the apt part costs time); `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` on the test step. WebKit is chosen through a hand-started run.
  - **Private repository:** GitHub-hosted runners have 2 vCPU (so `checksAtOnce` defaults to 2) and 2000 free Actions minutes a month (a run is a few runner-minutes); the README badge renders only for viewers with access.
- **Running the System Under Test:** The `mock-lab-app` ships its own Maven Wrapper (`mvnw`), so only a JDK is needed to build and run it. Locally: `cd mock-lab-app && ./mvnw spring-boot:run`. In CI (spec 006), each check job starts its own lab on its own runner VM with `.github/scripts/lab.sh start`: it builds the jar (`./mvnw -q package -DskipTests`; the jar name is fixed via the build's final name), starts it with `nohup java -jar … &`, and polls `GET /health` once a second for up to 60 s, failing early if the process dies. On timeout it writes a `::error` annotation and the tail of `lab-startup.log`. `lab.sh stop` runs with `if: always()`. `LAB_PORT` (default 8080) lets the script run locally beside an engineer's own lab. `/login` is not a valid readiness signal because the port opens before seed data is loaded. _Alternative: Docker Compose_, wrapping the mock app in a container for one-command startup — worth adopting only if local setup friction becomes a real problem, per "do not over-engineer."
- **Running the Checks:** Start the lab first (see above), then from the repo root: `./mvnw clean test` runs everything; `./mvnw -pl api-tests -am test` runs the checks that use the lab plus the framework's quick self-checks. `-am` (`--also-make`) is required because `test` does not install sibling modules, so plain `-pl api-tests` cannot resolve them on a clean machine; `install` and `-q` are deliberately not part of the documented flow. The checks never build, start or stop the lab. In CI (spec 006) each check job starts the lab, waits for `/health`, then runs its module the same way (see CI/CD above). Screen checks only: `./mvnw -pl ui-tests -am test` (reactor `common`, `test-data`, `api-client`, `ui-tests`). Since spec 005, subsets are picked with `-Dgroups` (see JUnit above). `./mvnw clean test` includes them; add `-fae` to get both verdicts when the API checks fail. `ui-tests` registers its own copy of the pre-flight listener, reusing `LabPreflight`.
- **Fail-Fast Pre-Flight:** A JUnit Platform `LauncherSessionListener` in `api-tests` checks once, before any test, that the lab answers `/health` and accepts the access key; otherwise the whole run stops with one greppable message (`LAB PRE-FLIGHT FAILED: …`) naming the address tried and how to start the lab. _Alternative: a per-class JUnit extension_ — rejected because it reports an error for every test class instead of stopping once. _Since spec 005:_ the listeners first validate the settings and log one banner (`key=***`), and run only for the first launcher session in the JVM, because self-tests that start a nested JUnit engine open more sessions in the same JVM.
- **Browser Automation Infra:** Playwright's bundled browser binaries, installed once with `./mvnw -N exec:java`. That command is `exec-maven-plugin` in the root POM with `<inherited>false</inherited>`, running Playwright's own CLI (`install chromium`) as a plugin dependency, so it needs no reactor build and no Node toolchain. On Linux CI, `-Dexec.args="install --with-deps <browser>"`. WebKit is installed once the same way, with `-Dexec.args="install webkit"`. The same plugin opens a trace: `-Dexec.args="show-trace <zip>"`. _Why not auto-download:_ `Playwright.create()` would silently fetch every browser, about 1 GB, inside the first test. So CI (spec 006) caches the browser folder and sets `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` for the test step (see CI/CD above). No Selenium Grid or separate browser provisioning is needed. _(There is no official `mvn playwright:install` plugin for Java; an earlier version of this document named one by mistake.)_

## 5. Observability & Reporting

- **Logging:** SLF4J + Logback across both the test framework and the mock app, capturing request method, endpoint, correlation/test ID, response status, and business identifiers — explicitly never credentials, tokens, or patient-identifying data, per the assignment's regulated-environment guidance. The mock app logs this way already; the test framework does too since spec 005:
  - `RequestLogFilter` (a RestAssured `Filter` in `api-client`, added to every request spec) writes one INFO line per request on logger `lab.http`: method, path, status, duration in ms, and the patient/order/sample identifiers from the path and the answer's id fields. It never writes headers (so never the access key), the query string, or names.
  - With `-DlogBodies=true` (or `LOG_BODIES`), request and answer bodies are also written, at DEBUG so they reach only the file, after `LogMasker` replaces every `name` and `password` value with `***`; a non-JSON body is logged only as its length.
  - `CheckNameInterceptor` (in `common`, registered on `LabTest` and `UiTest`) puts the check name into the SLF4J MDC, so every line can be found by searching for the check. It is an `InvocationInterceptor`, not a `beforeEach` callback, so it runs on the thread that executes the body, including the `SEPARATE_THREAD` timeout thread; MDC is thread-local, so it stays correct under parallel execution.
  - Logback in each test module: console at INFO, and `target/logs/api-tests.log` / `target/logs/ui-tests.log` at DEBUG for `lab.http`, rewritten each run and removed by `clean`. The pattern includes the thread name.
  - `NoConsolePrintingGuardTest` keeps `System.out`/`System.err`/`printStackTrace` out of the framework, and the lab-backed `RunLogSecrecyTest` proves the log file holds the sample identifier but neither the patient name nor the access key.
- **Test Reporting:** Maven Surefire reports and JUnit XML as the baseline (always available, no extra setup). Surefire's XML lists the JVM system properties, so secrets must never be passed as `-D` (see Configuration Management). _Alternative: Allure_, layered on top later if richer HTML reports become worth the added dependency and CI step.
- **Screen-check failure artifacts (spec 004):**
  - A failing screen check keeps a screenshot and a Playwright trace under `ui-tests/target/ui-failures/<browser>/<TestClass>/<scenario>/` (the browser level since spec 005, so a run in another browser never overwrites this one's evidence).
  - Folder names are built only from the browser name, the class name, the display name and the row index, never from argument values, so checks running side by side cannot collide.
  - Passing checks keep nothing.
  - The real password is kept out of traces. Experiments showed three leak paths: the `fill()` action log, DOM snapshots (Playwright records `type=password` values), and the network log of the sign-in POST. So sign-in (fill, submit, wait for the Sample List) runs with tracing stopped, and tracing restarts afterwards with the same options. `SignInTraceTest` proves that no trace entry holds the password. The trade-off is that a signed-in check's trace starts at the Sample List.
- **CI Test Summaries (spec 006):** `.github/scripts/junit_summary.py` (standard-library Python, always exits 0) turns each module's Surefire XML into Markdown: total/passed/failed/skipped/duration and each failing check by name with its expected-versus-actual. A `Summarise results` step (`if: always()`) pipes it through `tee -a "$GITHUB_STEP_SUMMARY"`, so it shows on the run page and in the job log. _Why not a marketplace reporter_ (e.g. `dorny/test-reporter`): check-run reporters need `checks: write`, which pull requests from forks do not get, and they add a third-party dependency to pin and trust.
- **CI Artifacts (spec 006):** uploaded with `if: always()`: `workflow-checks-results-<attempt>` and `screen-checks-results-<browser>-<attempt>` (Surefire reports, the run log, `lab-startup.log`); with `if: failure()`: `screen-failures-<browser>-<attempt>` (screenshots and traces). The run attempt in the name keeps a re-run from clashing with the first attempt. Retention is GitHub's 90-day default. GitHub does not mask artifact contents; secrets stay out because the framework never writes them (`RunLogSecrecyTest`, `SignInTraceTest`; grep-verified in Slice 5). Synthetic `TEST-` patient names may appear in screen evidence by design; in production, restrict access to such artifacts or mask that data.
