# System Architecture Overview: Lab Workflow SDET Automation Framework

---

## 1. Automation Framework & Language Stack

- **Language & Runtime:** Java 17 (LTS) — required by the assignment; LTS gives a stable, well-supported baseline for `record`-based domain models and modern language features.
- **Build Tool:** Maven, multi-module. **Four modules today** — `common` (the lab's shared concepts and configuration), `api-client` (the only code that talks to the lab's API), `api-tests` (the workflow checks) and, since spec 004, `ui-tests` (screen checks) — under a root parent `pom.xml` (groupId `com.labflow`). `test-data` from the assignment's recommended structure arrives later in Phase 2, when it has code (no empty placeholder modules). A **root Maven Wrapper** (`./mvnw`, script-only, Maven 3.9.11 — the same version as the lab's own wrapper) means only a JDK is needed. `maven.compiler.release=17` enforces Java 17 on any newer JDK (developed on JDK 26; CI will pin JDK 17 in Phase 3). Checks run under **Surefire** (settings at their defaults except for two deliberate changes, below), not Failsafe: they neither start nor stop the lab, so there is no teardown phase for Failsafe to protect and "one command" stays `test`. _Alternative: Failsafe_ — worth it if slow lab-dependent tests must later be separated from fast ones (or use tags in Phase 2).
  - **Readable names in reports (spec 004):** the root `pluginManagement` configures Surefire's JUnit 5 reporters (`JUnit5Xml30StatelessReporter`, `JUnit5StatelessTestsetInfoReporter`) with phrased names. Every module's `TEST-*.xml` then lists each check, including each parameterized row, under its `@DisplayName`. Report file names and the XML `classname` stay the Java class name, so tooling can still link results to source. Surefire's console never lists passing tests one by one.
  - **Whole-run time limit for `ui-tests` (spec 004):** the `surefire.timeout=600` property (Surefire's `forkedProcessTimeoutInSeconds`) kills a forked test JVM that is stuck for 10 minutes. It is set as a property rather than in the plugin `<configuration>`, so `-Dsurefire.timeout=…` can still override it.
- **Test Execution Framework:** JUnit 5 (Jupiter, the 5.14 line via the JUnit BOM) — parameterized tests, tags (`api`, `ui`, `smoke`, `regression`), and the built-in parallel execution engine. In Phase 1 parameterized tests are used sparingly, checks run in random order to prove independence, and tags and parallel execution arrive in Phase 2. **Time limits in layers (spec 004, `ui-tests`):**
  - Playwright caps every wait at 30 s.
  - JUnit caps each screen check at 2 minutes (`junit.jupiter.execution.timeout.default=2m`). A stuck check then fails under its `[Scenario: …]` name. The limit runs in `SEPARATE_THREAD` mode, because `SAME_THREAD` hung forever, in an experiment, on a wait that ignores interruption. The price is that the abandoned thread can disturb other checks in that one failing run.
  - Surefire's 10-minute fork limit (above) covers what JUnit cannot reach: the browser launch, `newContext`, tracing and `close` calls in extension callbacks. Playwright offers no timeout on those.
- **API Testing Library:** RestAssured 5.5.7 (confirmed in spec 003; the 5.x line matches JUnit 5 — RestAssured 6.x was not evaluated). _Alternative: Retrofit + OkHttp._ RestAssured is chosen as the default because it is purpose-built for test automation (fluent given/when/then assertions, minimal boilerplate for a small endpoint surface), whereas Retrofit is optimized for building typed production API clients — better justified if the design discussion leans toward "client-library" design.
- **Assertions & JSON Mapping:** AssertJ (fluent assertions, readable failure messages, and the base for the custom rejection assertions; the lab's own tests already use it) and Jackson (`databind` plus `jsr310` for `Instant`, one shared lenient mapper) — chosen over JUnit's built-in assertions and Hamcrest for failure-message quality.
- **Client Layering:** Test → Service → Api → RestAssured. Api classes make one call per lab endpoint and never assert; service classes expose business verbs in two forms — a "happy" method (returns a domain object, fails loudly on an unexpected status) and an `attempt…` twin (returns a response wrapper with status, headers and body, for scenarios where a refusal is the expected result). Custom AssertJ assertions (`isRejectedAs(kind, message)`) keep rejection checks readable. RestAssured types stay out of the checks (enforced by a guard test), and only per-request specs are used (no static RestAssured defaults), which keeps later parallel execution safe.
- **UI Automation Library:** Playwright for Java. _Alternative: Selenium WebDriver._ Playwright is the default given this repository's own name (`labflow-test-automation`), and it also ships auto-waiting and bundled browser binaries, reducing flakiness compared to hand-rolled Selenium waits — a plus for the "avoid flaky UI tests" evaluation criterion. Page Object Model applies equally well to either.
  - **Confirmed and built in spec 004:** Playwright for Java **1.63.0**, **Chromium only**, headless by default.
  - **`ui-tests` layout:**
    - Page Objects live in `src/main`: one per screen (`LoginPage`, `SampleListPage`, `CreateSamplePage`, `SampleDetailsPage`, `ReportPage`). JUnit and AssertJ are test-scoped, so the compiler keeps verdicts out of Page Objects.
    - Checks live in `src/test` (`happy/`, `rejection/`) and read as user workflows.
    - Navigation methods return the Page Object of the screen the user lands on. Outcomes are split by name (`signIn` vs `signInExpectingError`).
    - Only Page Objects know locators and screen URLs. Plain-text guard tests enforce this, as well as no fixed sleeps and no assertions in Page Objects.
  - **Test data:** each check prepares its data through `api-client`: a unique patient (the lab has no patient screen), and samples already partway through the workflow. Exactly one journey goes through every screen.
  - **Waiting:** Page Objects own synchronisation: each navigation returns only once the destination screen is ready, and `advance()` waits with `page.waitForCondition`. Checks compare resolved values with AssertJ. `PlaywrightAssertions` is not used.
  - **Browser lifecycle:** one `Playwright` + `Browser` per run, held in the root JUnit `ExtensionContext.Store`. A fresh `BrowserContext` + `Page` per test, which keeps it parallel-ready.
- **Optional BDD Layer (Phase 3):** Cucumber-JVM with Gherkin, for one or two demonstration scenarios only — kept minimal per the assignment's guidance not to over-invest here.

_Confirmed (spec 004): Playwright for Java over Selenium, Chromium only; Page Objects in `ui-tests/src/main`._

_Confirmed (spec 003): RestAssured over Retrofit + OkHttp. Java 17 is the baseline, enforced with `maven.compiler.release=17` so any newer JDK produces compatible bytecode._

## 2. System Under Test (Mock Lab Application)

_Phase 0 of the roadmap: since no real laboratory system exists to test against, this project builds its own minimal target application, kept structurally separate from the test framework itself._

- **Mock Backend Framework:** Spring Boot (Java) — a small REST service exposing the simulated lab workflow as JSON under the `/api` prefix (`/api/patients`, `/api/orders`, `/api/samples`) and enforcing the status state machine (Accessioned → ... → Report Generated), including the validation and error responses the negative test scenarios need. Processing progress, test result, and report are sample-scoped (`/api/samples/{id}/progress`, `/result`, `/report`) rather than separate top-level resources. A sample is moved to a requested stage with `PUT /api/samples/{id}/status`, and only the next stage is accepted. _Alternative: WireMock stub mappings or a Node.js `json-server`_ — simpler to stand up but harder to encode real state-transition logic and validation rules, which this project needs for meaningful negative testing.
- **URL Layout (JSON vs. screens):** The `/api` prefix keeps the JSON API apart from the Thymeleaf screens, which keep their own routes (`/samples`, `/samples/{id}`, `/samples/{id}/report`, `/login`). Both surfaces call the same service layer over the same in-memory data, so the lab rules are enforced identically and a sample created through either surface is visible in the other. _Alternative: serve JSON and HTML from the same paths via content negotiation_ — rejected because authentication behavior (redirect vs. 401) and error format would then depend on request headers.
- **Access Control (two isolated mechanisms, separated by path):** The screens use a session-based sign-in guard. The JSON API uses a shared access key sent as `Authorization: Bearer <key>`, checked by a servlet filter registered for `/api/*` only, with the key read from the `API_TOKEN` environment variable (a documented default applies for local runs; startup fails if it resolves to blank). The filter runs before routing, so a missing or wrong key yields 401 even for unknown routes or records. Neither mechanism reads the other's credentials. _Alternative: Spring Security_ — rejected as disproportionate for a mock target and out of line with the "no production-grade auth" non-goal.
- **Readiness Endpoint:** A small custom, unauthenticated `GET /health` returns 200 only once the application has finished starting **including** its seed data, and 503 before that. CI and local scripts poll it before running tests. _Alternative: Spring Boot Actuator's readiness probe_ — standard, but adds a dependency and needs extra security exclusions for no benefit at this scale.
- **Strict JSON Input:** The lab's JSON API parses request bodies strictly: a repeated key, or any content after the closing brace, is rejected as `400 "Malformed request body."` (Jackson strict duplicate detection and fail-on-trailing-tokens) rather than accepted leniently or failing with a server error. Test authors can rely on malformed-body checks behaving the same on every route.
- **In-Memory Data Store:** Plain in-memory Java collections (or H2 in-memory DB if persistence-like querying is useful). No external database — matches the assignment's explicit "no complicated databases" guidance. Relationships: a Patient has many Orders, an Order has many Samples (one sample per sample type per order), and each Sample has one Processing Job, one Test Result, and one Report once those stages are reached.
- **Front-End Framework:** A minimal server-rendered UI via Spring Boot + Thymeleaf, serving the Login, Sample List, Create Sample, Sample Details, and Report screens directly from the same mock backend. _Alternative: a small standalone React/plain-JS single-page app calling the backend's REST API._ Thymeleaf is the default to avoid standing up a second toolchain (Node/npm) purely to host a throwaway UI — consistent with "do not over-engineer."
- **Location in Repo:** Lives in its own `mock-lab-app/` module, separate from the Maven multi-module automation framework, since it is the system under test, not the thing being delivered as the "product."

_Assumption: Spring Boot + Thymeleaf for the mock app is a best-practice default balancing realism with the assignment's "keep it small" guidance — confirm before building._

_Assumption (spec 002): the API's URL layout, access-key scheme, readiness endpoint, and error mapping are detailed in `context/spec/002-mock-lab-rest-api/technical-considerations.md`; this document records only the architectural decisions. The assignment's own example `POST /samples` therefore becomes `POST /api/samples` (the test framework's `BASE_URL` stays a plain host, and the API client adds the `/api` prefix)._

## 3. Test Data & Configuration

- **Test Data Generation:** **Phase 1:** each check creates its own records with unique, `UUID`-suffixed names through a tiny helper in `api-tests`, never relying on another check or on global lab state (checks never assert global counts). **Phase 2:** reusable builders/factories (e.g. `PatientBuilder`, `SampleBuilder`) in the `test-data` module, using `java.util.UUID` to generate unique identifiers per test run and prevent collisions under parallel execution.
- **Test Data Storage:** None persisted between runs — all test data is ephemeral, created against the mock backend at test time and not required to survive beyond the run (traceability comes from correlation IDs in logs, not a database).
- **Configuration Management:** The lab address comes from the `-DbaseUrl` system property, else the `BASE_URL` environment variable, defaulting to `http://localhost:8080` (the framework adds the `/api` prefix). The access key comes **only from the `API_TOKEN` environment variable** — the same name the lab itself reads — defaulting to the lab's documented local key (`mock-lab-local-token`, not a secret). It is deliberately **never accepted as a system property**: a `-D` value is written into Surefire's XML reports and is visible in the process list. Everything is loaded through a small typed `LabConfig` in `common`; the key is wrapped in a type whose `toString()` is `***`, and RestAssured's logging blacklists the `Authorization` header. Since spec 004:
  - The screen checks sign in with `MOCK_LAB_USERNAME` / `MOCK_LAB_PASSWORD`, the same names the lab reads. The defaults are the lab's documented local values, `LabTech` / `I_Like_This_Lab`.
  - The password is **environment-only**, like the access key, and is wrapped in a masking `Password` type (`UiCredentials` in `ui-tests`).
  - `-Dheaded=true` shows the browser and `-DslowMo=<ms>` slows it down. Both are debugging aids, not secrets.
  - `BROWSER` and `ENVIRONMENT` still arrive with the Phase 2 configuration item. _Alternative: the Owner library_ for annotation-driven config binding — unnecessary at this project's scale.

## 4. Infrastructure & Deployment

- **CI/CD:** GitHub Actions, with separate `api-tests` and `ui-tests` jobs (plus a `build` job) so each can run and report independently.
- **Running the System Under Test:** The `mock-lab-app` ships its own Maven Wrapper (`mvnw`), so only a JDK is needed to build and run it. Locally: `cd mock-lab-app && ./mvnw spring-boot:run`. In CI (and for a plain jar run): `./mvnw -q package -DskipTests`, then `java -jar target/mock-lab-app.jar &` as a background step before the test jobs run (the jar name is fixed via the build's final name). Before tests start, the job waits for readiness by polling `GET /health` with `curl` retries (e.g. `curl -sf --retry 30 --retry-delay 1 --retry-connrefused http://localhost:8080/health`); `/login` is not a valid readiness signal because the port opens before seed data is loaded. _Alternative: Docker Compose_, wrapping the mock app in a container for one-command startup — worth adopting only if local setup friction becomes a real problem, per "do not over-engineer."
- **Running the Checks:** Start the lab first (see above), then from the repo root: `./mvnw clean test` runs everything; `./mvnw -pl api-tests -am test` runs the checks that use the lab plus the framework's quick self-checks. `-am` (`--also-make`) is required because `test` does not install sibling modules, so plain `-pl api-tests` cannot resolve them on a clean machine; `install` and `-q` are deliberately not part of the documented flow. The checks never build, start or stop the lab. In Phase 3 each CI job will start the lab, poll `/health`, then run its module the same way. Screen checks only: `./mvnw -pl ui-tests -am test` (reactor `common`, `api-client`, `ui-tests`). `./mvnw clean test` includes them; add `-fae` to get both verdicts when the API checks fail. `ui-tests` registers its own copy of the pre-flight listener, reusing `LabPreflight`.
- **Fail-Fast Pre-Flight:** A JUnit Platform `LauncherSessionListener` in `api-tests` checks once, before any test, that the lab answers `/health` and accepts the access key; otherwise the whole run stops with one greppable message (`LAB PRE-FLIGHT FAILED: …`) naming the address tried and how to start the lab. _Alternative: a per-class JUnit extension_ — rejected because it reports an error for every test class instead of stopping once.
- **Browser Automation Infra:** Playwright's bundled browser binaries, installed once with `./mvnw -N exec:java`. That command is `exec-maven-plugin` in the root POM with `<inherited>false</inherited>`, running Playwright's own CLI (`install chromium`) as a plugin dependency, so it needs no reactor build and no Node toolchain. On Linux CI, use `-Dexec.args="install --with-deps chromium"`. The same plugin opens a trace: `-Dexec.args="show-trace <zip>"`. _Why not auto-download:_ `Playwright.create()` would silently fetch every browser, about 1 GB, inside the first test. Phase 3 CI should cache the Playwright browser folder keyed on the Playwright version and set `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` for the test step. No Selenium Grid or separate browser provisioning is needed. _(There is no official `mvn playwright:install` plugin for Java; an earlier version of this document named one by mistake.)_

## 5. Observability & Reporting

- **Logging:** SLF4J + Logback across both the test framework and the mock app, capturing request method, endpoint, correlation/test ID, response status, and business identifiers — explicitly never credentials, tokens, or patient-identifying data, per the assignment's regulated-environment guidance. The mock app logs this way already; the test framework adopts it in **Phase 2** (the "Structured Logging" roadmap item). In Phase 1 the framework has no logger: secrecy is enforced by construction (the key type, the blacklisted header, failure messages that never include headers or request bodies).
- **Test Reporting:** Maven Surefire reports and JUnit XML as the baseline (always available, no extra setup). Surefire's XML lists the JVM system properties, so secrets must never be passed as `-D` (see Configuration Management). _Alternative: Allure_, layered on top later if richer HTML reports become worth the added dependency and CI step.
- **Screen-check failure artifacts (spec 004):**
  - A failing screen check keeps a screenshot and a Playwright trace under `ui-tests/target/ui-failures/<TestClass>/<scenario>/`.
  - Folder names are built only from the class name, the display name and the row index, never from argument values.
  - Passing checks keep nothing.
  - The real password is kept out of traces. Experiments showed three leak paths: the `fill()` action log, DOM snapshots (Playwright records `type=password` values), and the network log of the sign-in POST. So sign-in (fill, submit, wait for the Sample List) runs with tracing stopped, and tracing restarts afterwards with the same options. `SignInTraceTest` proves that no trace entry holds the password. The trade-off is that a signed-in check's trace starts at the Sample List.
- **CI Test Summaries:** GitHub Actions job summaries generated from the Surefire/JUnit XML output, showing total/passed/failed/skipped/duration directly in the workflow run.
